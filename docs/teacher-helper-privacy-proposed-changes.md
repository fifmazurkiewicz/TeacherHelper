# Teacher Helper — proposed privacy, RODO and AI changes

Status: **Implemented on 13 September 2026**

This document translates the general privacy and generative-AI plan into concrete changes for Teacher Helper. It is a product and technical proposal, not legal advice.

## 1. Recommended scope

The implementation should be divided into:

1. User-facing information that can be added as text and UI.
2. Privacy controls that must work in the backend and storage layer.
3. Legal and product decisions that must be approved before implementation.

The application already supports deletion of individual conversations, projects and files. It does not currently provide a public Privacy Policy route, contextual AI/privacy notices, account-wide export or deletion, or automatic retention enforcement.

## 2. Text and UI changes

### 2.1 Public Privacy Policy

Add a public `/privacy` route available without signing in.

The page should be available in Polish and English and explain:

- Who operates Teacher Helper and how to contact the controller.
- What account, conversation, upload, generated-content and technical data is collected.
- Why each data category is processed.
- The applicable legal basis for each purpose.
- Which verified providers receive data.
- Whether data is transferred outside the EEA and which safeguards apply.
- How long each category is stored.
- How users can access, export, correct and delete their data.
- How to complain to the supervisory authority.
- How AI is used and which information may be sent to AI providers.

Add links to the Privacy Policy from:

- Registration.
- Login.
- Profile.
- The main application navigation or footer.
- Contextual notices beside chat and upload controls.

The Privacy Policy should not contain promises that the implemented system cannot fulfil.

### 2.2 Registration notice

Add a short notice below the registration form:

> Creating an account requires processing your e-mail address and account information. Read the Privacy Policy to learn how Teacher Helper uses and protects your data.

Do not require users to “accept” the Privacy Policy as though it were optional consent. If Terms of Service are introduced, acceptance of the Terms should be handled separately.

### 2.3 Notice beside the assistant input

Display a compact notice near the message and upload controls:

> You are interacting with an AI system. Its responses may be inaccurate. Do not enter real student names, contact details, grades, disabilities, behavioural notes or confidential information. Use neutral labels such as “Student A” wherever possible.

The notice should:

- Be visible before the first message or upload.
- Remain readable on mobile.
- Link to the Privacy Policy.
- Not require confirmation before every message.

### 2.4 First-use AI disclosure

Before the first AI interaction, show a short disclosure explaining that:

- The assistant uses generative AI.
- User input and selected document excerpts may be sent to external providers.
- Generated results can be inaccurate, biased, incomplete or inappropriate for the intended age group.
- A teacher must review results before using them with students.

After the user acknowledges the disclosure, save the accepted disclosure version. Show it again only after a material change to the disclosure.

This is a small functional feature because the acknowledgement and disclosure version must be recorded.

### 2.5 AI-generated labels

Display a visible `AI-generated` / `Wygenerowane przez AI` label:

- Beside every assistant response.
- Beside generated worksheets, lesson plans, assessments and feedback.
- In previews and download areas for generated files.
- Inside exported materials or their metadata where practical and appropriate.

The label should not imply that uploaded source documents were generated by Teacher Helper.

### 2.6 Teacher-review and decision warning

Add this warning near generated educational materials:

> Review this material before use. AI-generated content may contain errors, bias or age-inappropriate information. Do not use AI output as the sole basis for final grading, admission, discipline or special-support decisions.

This is primarily text and UI. The product should also avoid introducing automated workflows that bypass meaningful teacher review.

## 3. Functional privacy changes

### 3.1 Privacy controls in Profile

Add a `Your data` / `Twoje dane` section to the Profile page.

It should provide:

- **Export my data**.
- **Delete all conversations**.
- **Delete all uploaded and generated materials**.
- **Delete my account**.
- A plain-language summary of retention periods.

Destructive actions should require clear confirmation. Account deletion should require recent authentication where supported by Supabase Auth.

### 3.2 Complete data export

`Export my data` should create a user-owned archive containing, as applicable:

- Account and profile information.
- Conversations and messages.
- Projects and topics.
- Uploaded files.
- Generated files and associated metadata.
- Consent or disclosure acknowledgement records.
- Relevant user-specific usage information.

The export should be generated asynchronously if necessary. The user should see its status and receive a time-limited authenticated download when it is ready.

### 3.3 Complete account deletion

Account deletion must cover more than the visible profile record. The backend should remove or anonymise, according to an approved policy:

- The Supabase Auth identity.
- The application user record.
- Conversations and messages.
- Projects and topics.
- Uploaded and generated storage objects.
- Extracted text and pgvector fragments.
- Active or queued generation jobs.
- User-specific limits and operational records.
- Observability data where deletion is technically and contractually supported.
- Backups according to the documented backup-expiry process.

The UI should explain what is deleted immediately and what may remain temporarily in protected backups.

Deletion must be tested end to end. A successful database cascade alone is insufficient if storage objects, external logs or authentication records remain.

### 3.4 Retention enforcement

Approve separate retention periods for:

- Conversations and messages.
- Uploaded files.
- Generated materials.
- Deleted-item remnants and temporary files.
- Generation jobs.
- LLM usage and cost records.
- Application and security logs.
- Langfuse traces when enabled.
- Database and storage backups.

Implement a scheduled cleanup process that deletes expired records and storage objects. The published Privacy Policy must use the same periods as the application configuration and cleanup code.

### 3.5 AI payload minimisation

Before calling an AI or media provider, the backend should construct the smallest payload needed for the selected task.

The normal behavior should be:

1. Receive the user request.
2. Select only relevant conversation context.
3. Retrieve only relevant document fragments through RAG.
4. Exclude unrelated profile, project, conversation and document data.
5. Send the reduced payload to the required provider.
6. Record only the operational and billing information that has an approved purpose and retention period.

Complete documents or complete user histories should not be sent when excerpts are sufficient.

### 3.6 Provider disclosure based on production configuration

The final Privacy Policy should describe only providers actually used in production. The review should verify the roles and configuration of at least:

- Supabase for authentication, Postgres and storage.
- Render for the backend.
- Vercel for the frontend.
- OpenRouter and the selected model providers.
- Langfuse when enabled.
- Tavily when web search is used.
- KIE when music generation is used.
- ElevenLabs when sound-effect generation is used.
- The configured video provider when video generation is enabled.

For each provider, record the data sent, purpose, processing region, retention/training configuration, subprocessor information and transfer safeguard. Unknown facts should be marked as unverified instead of inferred.

## 4. Decisions required before implementation

The following must be approved first:

- Controller identity and contact details.
- Whether Teacher Helper is strictly teacher-only.
- Whether students can create accounts or directly use the application.
- Intended user countries and supported policy languages.
- Whether schools use the service professionally.
- Controller/processor roles when teachers or schools upload student-related information.
- Exact retention periods for every data category.
- Actual production providers, regions and training/retention settings.
- Whether analytics or other non-essential trackers are enabled.
- Whether Terms of Service are required.
- Minimum user age and any child-user or guardian requirements.
- Final Polish and English wording.

Do not add student consent, parent consent, school-contract language or age-verification flows until the intended audience and legal roles are decided.

## 5. Proposed user flow

### Registration

1. The user sees the short privacy notice and a link to `/privacy`.
2. The user creates an account using e-mail or Google OAuth.
3. Privacy information is provided, but it is not represented as optional consent.

### First assistant use

1. The application displays the AI disclosure.
2. The user acknowledges the current disclosure version.
3. The assistant becomes available.
4. A compact privacy warning remains beside the chat and upload controls.

### Normal assistant use

1. The user enters a request and optionally selects files.
2. The backend selects only relevant context and document fragments.
3. The required provider receives the minimised payload.
4. The resulting response is visibly marked as AI-generated.
5. Generated educational material includes a teacher-review warning.

### Export

1. The user selects `Export my data` in Profile.
2. The backend creates an export job.
3. The Profile page displays its progress.
4. The user downloads the completed archive through a protected, time-limited link.

### Account deletion

1. The user selects `Delete my account`.
2. The application explains the impact and backup exception.
3. The user re-authenticates and confirms deletion.
4. The backend deletes data from Auth, Postgres, storage, indexes and active jobs.
5. The user is signed out and receives confirmation.

## 6. Recommended delivery order

### Phase A — discovery and decisions

- Map the real data flows and provider configuration.
- Decide controller details, audience, legal roles and retention periods.
- Approve Polish and English wording.

### Phase B — transparency UI

- Add `/privacy`.
- Add navigation and registration links.
- Add contextual privacy notices.
- Add first-use disclosure and AI-generated labels.
- Add teacher-review warnings.

### Phase C — privacy functionality

- Add complete data export.
- Add complete account deletion.
- Add bulk deletion controls.
- Add retention configuration and scheduled cleanup.
- Minimise and test provider payloads.

### Phase D — verification

- Test notices on desktop and mobile.
- Test Polish and English consistency.
- Test export and deletion end to end.
- Verify that deleted files disappear from storage and pgvector indexes.
- Verify that cleanup matches published retention periods.
- Inspect representative provider payloads to confirm minimisation.
- Verify every production policy link.

## 7. Important distinction

The following can be implemented primarily as text and UI:

- Privacy Policy.
- Registration notice.
- Chat and upload warning.
- AI-generated labels.
- Teacher-review disclaimer.
- Guidance to use `Student A` instead of real student identities.

The following must not be presented as working until backend behavior is implemented and tested:

- Complete data export.
- Complete account deletion.
- Automatic retention and cleanup.
- Consent or disclosure-version records.
- AI payload minimisation.
- Blocking non-essential trackers before consent.
- Removal from external observability systems and eventual backup expiry.
